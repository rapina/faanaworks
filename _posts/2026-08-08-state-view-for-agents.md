현재 상태 화면을 브라우저로 열었을 때는 꽤 든든했어요. 왼쪽에는 아이템과 괴이, 조작과
밸런스 목록이 줄지어 있었고, 이름을 검색하면 관련 표만 남았어요. 서로 떨어진 수치 세트는
화면 첫머리의 그래프에서 함께 움직였고요.

이 화면은 사람과 에이전트가 게임의 현재 값을 같은 곳에서 보게 하려고 만들었어요. 그런데
작업 기록을 다시 훑어보니 에이전트가 이 화면을 판단에 썼다는 흔적은 드물었어요. 값을
바꾼 뒤 다시 구웠다는 기록은 많았지만, 작업을 시작하며 여기서 현재 상태를 확인했다는
기록은 거의 없었어요.

처음 든 생각은 간단했어요. 에이전트에게는 이런 화면이 필요 없는 걸까.

## 같은 파일이면 같은 도구가 될 줄 알았다

현재 상태 화면은 손으로 옮겨 적은 표가 아니에요. 게임을 직접 부팅해 엔진이 읽은 상수와
목록을 모으고, 값 가까이에 있던 설명까지 한 HTML에 굽고 있어요. 원본이 바뀌면 해시로
뒤처짐을 확인하고, 작업 검증 과정에서 다시 만들어요. 낡은 표를 최신인 것처럼 보여 주지
않으려는 장치도 있었어요.

사람에게는 이 정도면 충분했어요. 파일을 열면 목차와 검색창이 있고, 값의 모양에 맞춰
표가 펴져요. 전체를 훑다가 이상한 숫자를 발견하거나, 이름을 아는 항목으로 바로 갈 수
있어요.

에이전트가 받은 것은 같은 화면의 원문이었어요. 데이터는 들어 있었지만 그 앞뒤로 HTML,
CSS, 화면을 그리는 코드가 함께 있었어요. 8천 줄이 넘는 파일에서 값 몇 개를 찾는 것보다
원본 소스를 검색하는 편이 빨랐어요. 더구나 실제 수정에는 값만으로 부족해요. 누가 그 값을
읽는지, 언제 적용하는지, 어떤 검사가 지키는지도 알아야 하니까요.

같은 파일을 건넸지만 사람에게는 화면이었고 에이전트에게는 큰 문서였어요.

## 모든 작업에 읽게 하지는 않았다

가장 쉬운 처방은 작업을 시작할 때마다 전체 파일을 읽으라고 쓰는 일이었어요. 그러면
사용했다는 흔적은 늘겠지만, 화면 배치나 입력 버그를 고칠 때도 큰 상태표를 먼저 통과해야
해요. 필요 없는 읽기가 계약이 되면 에이전트는 지키더라도 판단에는 쓰지 않게 돼요.

대신 질문의 종류를 좁혔어요. 현재 수치, 목록, 밸런스, 콘텐츠 구성을 다루는 작업만 이
화면에서 시작해요. 제어 흐름이나 렌더링 문제는 계속 해당 소스로 바로 가고요.

기계용 입구도 붙였어요. 검색어 몇 개를 주면 HTML 전체 대신 관련 스칼라 값, 그 값이 놓인
데이터 경로, 선언을 실은 소스 위치만 짧게 돌려줘요. 검색어가 둘이면 둘 다 들어 있는
결과만 남고, 너무 넓게 찾았을 때는 출력 수를 제한해요. 화면이 뒤처졌다면 검색 결과를
내지 않고 먼저 다시 만들라고 멈춰요.

사람용 화면과 기계용 검색은 같은 데이터 묶음을 읽어요. 별도 JSON을 하나 더 두면 두
입구가 언젠가 서로 다른 현재를 말할 수 있어서, 이미 HTML 안에 구워 둔 값을 그대로
사용했어요.

## 값 하나보다 관계가 필요할 때

기계용 검색이 생겨도 현재 상태 화면이 사람 전용으로 남는 부분은 있어요. 검색은 이름을
아는 값을 빠르게 찾지만, 서로 다른 이름 아래 있는 값의 관계를 먼저 제안하지는 못해요.

공황 회복 문제가 그랬어요. 심호흡에 필요한 시간과 발작 사이 행동 시간은 각각 자기
자리에서는 그럴듯했지만, 함께 놓으면 심호흡이 끝나기 전에 다음 발작이 왔어요. 화면의
공황 그래프는 두 값을 겹쳐 회복 뒤에 몇 초가 남는지 보여 줘요. 이 관계는 게임 안에서
요원이 실제로 숨을 고를 수 있는지로 이어져요.

에이전트는 검색 결과에서 현재 값을 확인하고 소스로 들어가요. 사람은 화면에서 목록을
훑고 그래프를 움직여 봐요. 한쪽이 다른 쪽을 흉내 내게 하지 않고, 같은 현재 값까지 가는
입구만 각자 손에 맞게 나눈 셈이에요.

## 아직 사용 여부는 보이지 않는다

검색 명령과 읽기 규칙을 붙였다고 해서 에이전트가 판단에 활용한다는 보장은 없어요. 파일을
읽은 행위는 작업 결과에 남지 않을 수 있고, 매번 사용 여부를 적게 하면 다시 체크 항목만
늘어나요.

앞으로 볼 것은 기록 문구보다 작업의 출발점이에요. 값이나 목록을 다루는 변경에서 처음
찾은 범위가 맞는지, 서로 떨어진 항목을 놓치지 않는지, 소스에 들어가기 전에 현재 값을
확인했는지를 살펴보려고 해요. 기계용 검색이 값 찾기에는 충분해도 관계를 찾는 데는 여전히
약한지도 남아 있어요.

현재 상태 화면은 그대로예요. 달라진 것은 에이전트가 그 앞에서 8천 줄짜리 문을 밀지
않아도 된다는 점이에요.
