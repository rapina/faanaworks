같은 게임이 데스크톱에서도 돌고 브라우저에서도 돕니다. 어느 쪽이 무거운지 물으려면 두
쪽을 같은 자로 재야 하는데, 처음 막힌 건 성능이 아니라 **숫자를 꺼내는 길**이었어요.
데스크톱은 게임이 찍은 줄을 표준 출력에서 읽으면 됩니다. 브라우저에는 그 표준 출력이
없어요. 개발자 도구 콘솔 안에 갇혀 있고, 그걸 여는 건 사람이죠.

이 글은 그래서 어떻게 짰는지를 적은 기술 문서예요. 순서는 기록 → 전송 → 장면 → 지표 →
대조 → 거부 조건 → 조회입니다.

## 1. 기록은 한 줄의 JSON입니다

계측이 끝나면 엔진이 사람용 요약 여러 줄과 **별개로** 기계용 한 줄을 찍습니다. 접두사
하나와 JSON 하나예요.

```
[PERF-JSON] {"schema":1,"scene":"traverse","platform":"Web", ... }
```

한 줄인 이유는 전송 때문입니다. 뒤에 나오는 웹 경로가 줄 단위로 회수하거든요. 여러 줄에
걸치면 조립하는 코드가 양쪽에 하나씩 더 생기고, 그 둘이 언젠가 갈립니다.

기록에 담는 건 네 묶음이에요.

```jsonc
{
  "schema": 1,
  // 어디서 잰 것인가
  "platform": "Web", "renderer": "gl_compatibility",
  "adapter": "WebKit WebGL", "cores": 2,
  "timer_us": 100,        // 이 플랫폼의 시계 눈금
  "display_hz": null,     // 못 잰 값은 0이 아니라 null
  "vsync_request": "disabled",

  // 무엇을 재게 했는가
  "scene": "traverse", "seconds": 30.0, "frames": 1826,
  "warmed": true, "warm_frames": 19,
  "world": { "map_w": 96, "buildings": 33, "entities": 24,
             "travel_tiles": 43.8, "travel_turns": 2 },

  // 잰 값
  "render": { "cpu_ms_avg": 1.80, "gpu_ms_avg": null,
              "draw_calls_avg": 288.3, "objects_avg": 497.8 },
  "probe":  { "update_frame": { "avg_ms": 2.78, "max_ms": 25.06 },
              "compute_light": { "avg_ms": 1.05, "max_ms": 5.79 } },
  "frame_ms": { "p50": 16.7, "p95": 17.4, "over_40": 5, "over_40_ms": 243 },

  // 무엇을 못 쟀는가
  "unavailable": ["display_hz", "render.gpu_ms"]
}
```

**`unavailable`이 이 스키마에서 제일 중요한 항목이에요.** 그래픽 처리 시간을 물으면
0.0이 돌아오는 자리가 있습니다. GPU가 0밀리초인 게 아니라 측정이 안 되는 거예요. 그걸
0으로 적어 두면 나중에 그 0을 보고 "여긴 비용이 없구나" 하거나, 더 나쁘게는 없는 수치를
줄이려고 달려듭니다. 그래서 후보 항목 목록을 따로 두고, 값이 0 이하로 돌아오면 `null`로
바꾼 뒤 그 경로를 `unavailable`에 적습니다.

`timer_us`도 같은 이유예요. 브라우저는 고해상도 시계를 잘라서 줍니다. 실제로 재 보니
100마이크로초 눈금이었어요. 그 아래 구간은 0으로 읽히니까, 웹에서 잰 작은 값이
데스크톱보다 작다고 웹이 빠른 게 아닙니다. 눈금을 재는 방법은 단순해요 — 시계를 읽고,
값이 바뀔 때까지 읽고, 그 차이를 적습니다.

## 2. 전송만 두 갈래로 가릅니다

**재는 코드는 한 벌이고 다른 것은 그 줄이 나가는 길뿐**이라는 게 이 구성의 기본 규칙이에요.

데스크톱은 간단합니다. 실행기가 게임을 자식 프로세스로 띄우고 표준 출력에서 접두사로
시작하는 줄을 찾아 JSON을 파싱해요.

브라우저는 세 단계가 필요했습니다.

**첫째, 실행 인자를 페이지에 심습니다.** 웹 내보내기는 `index.html` 안에 엔진 설정
객체를 두는데, 거기 인자 배열이 있어요. 내보낸 뒤 그 배열을 원하는 값으로 치환합니다.
같은 방식으로 캔버스 크기 정책도 고정해서, 창 크기에 따라 해상도가 달라지지 않게 했어요.
해상도가 흔들리면 그리기 비용이 흔들립니다.

```js
// 내보낸 페이지의 설정을 치환한다
"args":["--","perf","scene=traverse"]
"canvasResizePolicy":0
```

**둘째, 콘솔을 가로챕니다.** 엔진 시작 직전에 `console.log`를 감싸서, 정해진 접두사로
시작하는 줄만 로컬 수집 서버로 보내요.

```js
const origin = console.log.bind(console);
console.log = (...args) => {
  origin(...args);
  const line = args.map(String).join(" ");
  if (line.startsWith("[PERF") || line.startsWith("[SPIKE")) {
    fetch("/__perf", { method: "POST", body: line }).catch(() => {});
  }
};
```

여기서 한 번 발이 걸렸어요. 튀는 프레임을 하나씩 뜯어 보는 진단 줄을 새로 만들었는데
웹에서 아무것도 안 왔습니다. 필터가 접두사 하나만 통과시키고 있었어요. **새 진단 줄의
접두사를 이 조건에 넣지 않으면 브라우저 콘솔에만 남고 회수되지 않습니다.** 이미 심어 둔
페이지도 갱신되도록, 다시 심을 때 기존 조건식을 찾아 바꾸는 경로를 따로 뒀어요.

**셋째, 정적 서버 겸 수집 서버를 띄웁니다.** 내보낸 디렉터리를 그대로 서비스하면서
`POST /__perf`를 받아 큐에 넣는 작은 HTTP 서버예요. 실행기는 임의 포트로 서버를 올리고,
헤드리스 브라우저를 그 주소로 띄우고, 큐에서 줄을 꺼냅니다.

```
실행기 ── 내보내기 ── index.html 치환 ── 로컬 서버(정적 + POST)
                                            │
                            헤드리스 브라우저 ┘  →  줄 큐  →  JSON 파싱
```

브라우저 종료 판정은 두 조건으로 했어요. 프로세스가 죽거나, **마지막 줄이 온 뒤 조용한
시간이 일정 시간을 넘거나.** 게임이 스스로 종료하지 않는 모드가 있어서 프로세스 종료만
기다리면 매번 제한 시간을 다 씁니다.

## 3. 장면은 엔진이 소유하고 이름으로 부릅니다

두 플랫폼이 같은 숫자를 내려면 같은 것을 해야 합니다. 처음엔 실행 인자를 손으로 맞췄는데
그러면 반드시 갈려요. 그래서 장면 표를 엔진 코드 한 곳에 두고 이름 하나로 부르게 했어요.

```
base            (아무 인자 없음)
traverse        30초 동안 한 방향으로 걷다 막히면 방향 전환 + 로딩 워밍
traverse_large  같은 것을 네 배 넓은 도시에서
interior        실내에 세워 둠
```

실행기는 이 목록을 복제하지 않습니다. 게임한테 물어봐요 — 목록만 찍고 종료하는 모드를
하나 두고, 실행기가 그걸 호출해서 이름을 받습니다. 목록이 두 곳에 있으면 언젠가 한쪽만
낡거든요.

이동 방식은 두 번 고쳤어요. 처음엔 여덟 방향으로 고르게 도는 것이었는데, 그러면 출발점
주변만 계속 다시 그립니다. 새 영역에 들어서는 비용이 안 잡혀요. 지금은 이렇게 합니다.

```
방향 ← 초기값
0.5초마다:
    그 방향으로 이동 입력을 준다
    이번 구간에 실제로 움직인 거리를 잰다
    누적 거리에 더한다
    움직인 거리가 0.6타일 미만이면 (막힌 것)
        방향을 108도 돌린다
```

108도인 이유는 90도나 180도로 돌리면 왔던 길을 되짚기 쉬워서예요. 그리고 **누적 거리를
기록에 남깁니다.** 이게 없으면 벽에 붙어 제자리걸음한 측정이 "튀는 프레임이 적다"로
읽히고, 그게 개선처럼 보입니다.

장면에는 로딩 화면을 거치는 선택지도 넣었어요. 이 게임은 로딩이 덮여 있는 동안 플레이어를
여러 지점으로 옮겨 가며 미리 몇 프레임씩 그려 둡니다. 계측 모드는 그 로딩을 건너뛰고
있었어요. **실제 플레이어가 내지 않는 비용을 함께 재고 있었던 겁니다.** 지금은 같은 길로
들어가고, 어느 쪽이었는지를 기록에 남깁니다.

## 4. 무엇을 재는지가 절반이었어요

처음에는 프레임이 17.5밀리초를 넘긴 횟수를 셌습니다. 사람이 느끼는 것에 가깝다고
생각했어요.

못 씁니다. 브라우저는 화면 주사율에 맞춰 프레임을 밀어 주기 때문에 프레임 시간이
16.7밀리초 근처에 몰려요. 거기서 "몇 번 넘었나"를 세면 아슬아슬하게 걸친 프레임이 그날의
사소한 사정에 따라 넘거나 안 넘거나 합니다. 아무것도 바꾸지 않은 쪽이 한 세션에 266,
다음 세션에 45를 냈어요.

그래서 **창 전체에 걸쳐 프레임마다 누적**하는 값으로 바꿨습니다. 프레임 콜백에 훅을 걸고
거기서 더해요.

```
매 프레임:
    누적_렌더CPU += 뷰포트 렌더 CPU 시간 + 프레임 셋업 시간
    누적_드로우콜 += 이번 프레임 드로우콜
    프레임수 += 1

기록: cpu_ms_avg = 누적_렌더CPU / 프레임수
```

주의할 점이 하나 있어요. 렌더 시간 측정은 켜야 값이 나오는데, 그걸 **측정 창이 시작되기
전에** 켜야 합니다. 끝날 때 한 번 켜고 읽으면 그 순간 한 프레임의 값만 얻어요.

이렇게 바꾸자마자 같은 조건 두 번이 0.02밀리초 안에서 맞아떨어졌습니다. 순간값은 여전히
기록하되 판정에는 쓰지 않아요 — 측정이 끝난 그 프레임 하나라 서 있는 자리에 따라 40씩
흔들립니다.

프레임 시간 계수도 지우지는 않았어요. 경향을 보는 눈금으로는 쓰고, **회귀 판정에는 쓰지
않는다**고 문서에 적어 뒀습니다.

## 5. 대조는 번갈아, 폭은 그날 잽니다

숫자가 안정돼도 "좋아졌다"고 말하려면 기준이 필요해요. 이 기계는 다른 일도 하고 있으니까
30분 전과 지금이 다릅니다.

그래서 고친 쪽과 원래 쪽을 번갈아 잽니다.

```
for 라운드 in 1..N:
    측정(브랜치)   → 기록 목록 A에 추가
    측정(기준)     → 기록 목록 B에 추가

각 지표에 대해:
    이전 = median(B),  이후 = median(A)
    폭  = max(퍼짐(A), 퍼짐(B))      # 퍼짐 = (최댓값 - 최솟값) / 2
    |이후 - 이전| > 폭 이면 유의미한 이동
```

한쪽을 네 번 몰아서 돌리고 다른 쪽으로 넘어가면, 그 사이에 기계 상태가 흘러간 만큼이
그대로 차이로 읽혀요. A·B·A·B로 돌리면 그 흐름이 양쪽에 고르게 묻습니다.

**노이즈 폭을 고정값으로 정하지 않은 게 핵심이에요.** 같은 쪽 안에서 값이 얼마나
벌어졌는지를 그날 그때 재서 그걸 폭으로 씁니다. 임계를 손으로 정하면 그 숫자가 어디서
왔는지 아무도 설명하지 못하게 되거든요.

라운드는 넷 이상을 씁니다. 둘로 하면 퍼짐이 두 점 사이 간격이라 폭이 좁게 잡히고, 아무
이동이나 유의미해 보여요. 실제로 같은 코드를 두 라운드로 대조했더니 한 지표가 폭 밖으로
나갔습니다.

기준 쪽은 별도 작업 폴더에 받아 둔 main을 씁니다. 같은 폴더에서 코드를 되돌려 가며 재면
빌드 캐시가 섞여요.

## 6. 사람이 없을 때 스스로 거부하는 자리

여기까지가 "잰다"이고, 사람 없이 돌리려면 **틀린 숫자를 스스로 거부하는 자리**가 더
필요했어요. 넷을 넣었습니다.

**다른 계측이 돌고 있으면 거부합니다.** 프로세스 목록에서 게임 엔진과 헤드리스 브라우저를
찾아 이름으로 거릅니다. 실제로 다른 작업의 화면 촬영 두 개가 겹쳤을 때 양쪽 다 13분 동안
한 프레임도 못 나간 적이 있어요. 남의 프로세스를 죽이지는 않습니다 — 무엇이 누구 것인지
알 수 없으니까요. 기다리거나, 강제 진행 옵션을 쓰되 그 숫자는 기준이 아니라고 함께
적습니다.

**두 쪽이 같은 거리를 걷지 않으면 대조를 거부합니다.** 누적 이동 거리가 25% 넘게 벌어지면
멈춰요. 걸은 거리가 다른 두 측정의 스파이크 수는 비교할 수 없습니다.

**재고가 없으면 무엇을 돌려야 하는지 답합니다.** 기록은 저장소에 커밋하지 않아요. 다른
기계나 다른 작업 폴더에는 없는 게 정상입니다. 조회 도구가 빈 손으로 통과하는 대신, 무엇을
실행하라고 말하고 실패 코드를 냅니다.

**게이트에는 넣지 않았어요.** 성능은 부하에 흔들리니까 필수 검사에 넣으면 언젠가 그
검사를 무르게 고치게 됩니다. 대조기의 종료 코드는 참고값이고, 성능을 건드린 변경은 그
출력을 변경 설명에 붙이는 걸로 정했어요.

## 7. 읽는 쪽은 수치 옆에 위치를 냅니다

쌓인 기록을 통째로 읽는 건 저한테도 무리예요. 그래서 묻는 도구를 뒀습니다. 장면 하나의
프레임 예산 분해, 이름 조각으로 찾기, 두 시점 사이의 이동, 그리고 기계가 먹는 형태.

거기서 한 가지를 더 했어요. **각 줄 옆에 그 측정이 심어진 소스의 파일과 줄 번호를 함께
냅니다.** 하위 시스템 시간은 소스에 박아 둔 이름표로 모이는데, 그 이름표 문자열을 소스
전체에서 찾아 위치를 붙이는 거예요.

```
update_frame     3.871 ms (34.8%)  max 25.061 ms · <그 이름표가 있는 파일:줄>
view.sync        1.541 ms (13.9%)  max  8.165 ms · <그 이름표가 있는 파일:줄>
```

어떤 항목이 프레임의 35퍼센트를 먹는다는 걸 알아도, 그 다음에 어디를 열어야 할지 다시
찾아야 하면 그 사이에서 판단이 흐려지더라고요.

시계 눈금의 세 배 미만인 값에는 잡음 표시를 붙입니다. 웹은 눈금이 100마이크로초니까
0.3밀리초 아래가 여기 걸려요.

## 왜 이렇게까지 했나

처음엔 이 절반도 안 만들었어요. 자를 대충 세우고 바로 게임 코드를 열었습니다. 그리고
없는 원인을 하나 찾아서 고쳤어요. 실내 소품이 부하의 열 배 원인이라고 믿었는데, 나중에
안정된 자로 다시 재니 그 장면에는 실내 소품이 애초에 그려지지도 않고 있었습니다.

사람이 매번 결과를 들여다보고 "이건 좀 이상한데" 하고 잡아 주는 측정이라면 대충 만들어도
돌아갑니다. 사람 없이 돌리려면 그 "이상한데"를 코드로 심어 둬야 해요. 노이즈 폭, 걸은
거리, 부하 감지, 못 잰 값 표시. 전부 제가 저를 못 믿어서 넣은 것들입니다.

아직 못 하는 것도 있어요. 측정은 전부 빠른 기계에서 나왔습니다. 여기서 무의미한 수가
낡은 노트북에서는 다른 이야기일 텐데, 그건 여기서 확인할 방법이 없어요. 그래서 "여기서는
의미 없다"까지만 적어 두고 있습니다.
