같은 게임이 데스크톱에서도 돌고 브라우저에서도 돕니다. 어느 쪽이 무거운지 물으려면 두
쪽을 같은 자로 재야 하는데, 처음 막힌 건 성능이 아니라 **숫자를 꺼내는 길**이었어요.
데스크톱은 게임이 찍은 줄을 표준 출력에서 읽으면 됩니다. 브라우저에는 그 표준 출력이
없어요. 개발자 도구 콘솔 안에 갇혀 있고, 그걸 여는 건 사람이죠.

이 글은 그래서 어떻게 짰는지를 적은 기술 문서예요. 붙인 출력은 전부 실제로 나온
것이고, 저장소 경로만 가렸습니다.

## 전체 그림

```
                     ┌─────────────────────────┐
                     │  장면 표 (엔진이 소유)   │
                     │  base · traverse · …    │
                     └────────────┬────────────┘
                        이름으로 부름 │  목록은 엔진에 물어봄
                                    ▼
  ┌──────────────────────────  실행기  ──────────────────────────┐
  │                                                              │
  │  desktop                          web                        │
  │  ────────                         ────────                   │
  │  엔진을 자식 프로세스로 실행       내보내기(export)            │
  │         │                          → index.html 인자 치환     │
  │         │                          → 로컬 서버(정적 + POST)   │
  │         │                          → 헤드리스 브라우저 실행    │
  │         │                          → console.log 후킹         │
  │         ▼                                  │                 │
  │    표준 출력                          POST /__perf            │
  │         └──────────┐          ┌────────────┘                 │
  │                    ▼          ▼                              │
  │              "[PERF-JSON] {…}" 한 줄 파싱                     │
  └────────────────────────────┬─────────────────────────────────┘
                               ▼
                  build/perf/<platform>.jsonl  (append)
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
        조회 도구                            대조기
   (분해 · 질의 · JSON)              (A·B·A·B 교대 · 노이즈 폭)
```

## 1. 기록은 한 줄의 JSON입니다

계측이 끝나면 엔진이 사람용 요약 여러 줄과 **별개로** 기계용 한 줄을 찍습니다. 한 줄인
이유는 전송 때문이에요. 웹 경로가 줄 단위로 회수하거든요. 여러 줄에 걸치면 조립하는 코드가
양쪽에 하나씩 더 생기고, 그 둘이 언젠가 갈립니다.

실제로 나온 기록이에요. 길어서 프로브 두 개만 남기고 잘랐습니다.

```json
{
 "schema": 1,
 "platform": "macOS", "renderer": "forward_plus",
 "timer_us": 1, "display_hz": 60.0, "vsync_request": "disabled",
 "scene": "traverse", "seconds": 30.645, "frames": 2733, "warmed": true,
 "world": {
  "map_w": 96, "buildings": 33, "entities": 24,
  "travel_tiles": 41.7812433540821, "travel_turns": 5
 },
 "render": {
  "cpu_ms_avg": 0.2, "gpu_ms_avg": 0.0,
  "draw_calls_avg": 291.656, "objects_avg": 514.139
 },
 "frame_ms": {
  "p50": 6.973, "p95": 17.011, "p99": 17.444,
  "over_17_5": 23, "over_40": 0, "samples": 2806
 },
 "probe": {
  "update_frame": { "avg_ms": 2.359, "max_ms": 34.234 },
  "compute_light": { "avg_ms": 1.121, "max_ms": 2.465 }
 },
 "unavailable": ["render.gpu_ms"]
}
```

네 묶음이에요. **어디서 잰 것인가**(`platform`·`renderer`·`timer_us`·`display_hz`),
**무엇을 재게 했는가**(`scene`·`world`·`warmed`), **잰 값**(`render`·`probe`·`frame_ms`),
**무엇을 못 쟀는가**(`unavailable`).

`unavailable`이 이 스키마에서 제일 중요한 항목이에요. 위 기록을 보면 `gpu_ms_avg`가
0.0인데, GPU가 0밀리초인 게 아니라 이 플랫폼에서 측정이 안 되는 겁니다. 0으로 두면
나중에 그 0을 보고 "여긴 비용이 없구나" 하거나, 더 나쁘게는 없는 수치를 줄이려고
달려들어요. 그래서 후보 항목 목록을 미리 정해 두고, 값이 0 이하로 돌아오면 그 경로를
`unavailable`에 적습니다.

같은 장면을 브라우저에서 재면 `unavailable`이 이렇게 늘어나요.

```json
"platform": "Web", "renderer": "gl_compatibility",
"timer_us": 100, "display_hz": null,
"unavailable": ["display_hz", "render.gpu_ms", "engine_ms.nav"]
```

`timer_us`가 데스크톱 1에서 웹 100으로 바뀐 걸 보세요. 브라우저는 고해상도 시계를 잘라서
줍니다. 그 아래 구간은 0으로 읽히니까, 웹에서 잰 작은 값이 데스크톱보다 작다고 웹이 빠른
게 아니에요. 재는 방법은 단순합니다 — 시계를 읽고, 값이 바뀔 때까지 다시 읽고, 그 차이를
적습니다.

## 2. 전송만 두 갈래로 가릅니다

**재는 코드는 한 벌이고 다른 것은 그 줄이 나가는 길뿐**이라는 게 기본 규칙이에요.

데스크톱은 간단합니다. 게임을 자식 프로세스로 띄우고 표준 출력에서 접두사로 시작하는 줄을
찾아 파싱해요.

브라우저는 세 단계가 필요했습니다.

**첫째, 실행 인자를 페이지에 심습니다.** 웹 내보내기는 `index.html` 안에 엔진 설정 객체를
두는데 거기 인자 배열이 있어요. 내보낸 뒤 그 배열을 정규식으로 치환합니다. 캔버스 크기
정책도 같이 고정했어요 — 창 크기에 따라 해상도가 달라지면 그리기 비용이 흔들립니다.

```js
"args":["--","perf","scene=traverse"]
"canvasResizePolicy":0
```

**둘째, 콘솔을 가로챕니다.** 엔진 시작 직전에 `console.log`를 감싸서, 정해진 접두사로
시작하는 줄만 로컬 수집 서버로 보내요.

```js
const origin = console.log.bind(console);
console.log = (...args) => {
  origin(...args);
  const line = args.map(String).join(" ");
  if (line.startsWith("[PERF") || line.startsWith("[SPIKE")) {
    fetch("/__perf", { method: "POST", body: line }).catch(() => {});
  }
};
```

여기서 한 번 발이 걸렸어요. 튀는 프레임을 뜯어 보는 진단 줄을 새로 만들었는데 웹에서
아무것도 안 왔습니다. 이 조건이 접두사 하나만 통과시키고 있었어요. **새 진단 줄의 접두사를
여기 넣지 않으면 브라우저 콘솔에만 남고 회수되지 않습니다.** 이미 심어 둔 페이지도
갱신되도록, 다시 심을 때 기존 조건식을 찾아 바꾸는 경로를 따로 뒀어요.

**셋째, 정적 서버 겸 수집 서버를 띄웁니다.** 내보낸 디렉터리를 서비스하면서 `POST
/__perf`를 받아 큐에 넣는 작은 HTTP 서버예요. 임의 포트로 올리고, 헤드리스 브라우저를 그
주소로 띄우고, 큐에서 줄을 꺼냅니다.

브라우저 종료 판정은 두 조건으로 했어요. 프로세스가 죽거나, **마지막 줄이 온 뒤 2초 동안
아무 줄도 안 오거나.** 스스로 종료하지 않는 모드가 있어서 프로세스 종료만 기다리면 매번
제한 시간을 다 씁니다.

## 3. 장면은 엔진이 소유하고 이름으로 부릅니다

두 플랫폼이 같은 숫자를 내려면 같은 것을 해야 합니다. 처음엔 실행 인자를 손으로 맞췄는데
그러면 반드시 갈려요. 그래서 장면 표를 엔진 코드 한 곳에 두고 이름으로 부릅니다.

```
$ perf-run --list
[PERF RUN] 장면 base city_large fog interior move senses traverse traverse_large
```

실행기는 이 목록을 복제하지 않아요. 목록만 찍고 종료하는 모드를 엔진에 하나 두고, 그걸
호출해서 이름을 받습니다. 목록이 두 곳에 있으면 언젠가 한쪽만 낡거든요.

한 번 재면 이렇게 나옵니다.

```
$ perf-run --scene traverse
[PERF RUN] desktop · traverse
[PERF RUN] macOS traverse · fps 89.2 · p95 17.0ms · p99 17.4ms
           · update_frame 2.36ms · compute_light 1.12ms · view.sync 0.64ms
           · 못 잰 것 render.gpu_ms
[PERF RUN] 저장 build/perf/macos.jsonl
```

이동 방식은 두 번 고쳤어요. 처음엔 여덟 방향으로 고르게 도는 것이었는데, 그러면 출발점
주변만 계속 다시 그립니다. 새 영역에 들어서는 비용이 안 잡혀요. 지금은 이렇게 합니다.

```
방향 ← 초기값
0.5초마다:
    그 방향으로 이동 입력을 준다
    이번 구간에 실제로 움직인 거리를 잰다
    누적 거리에 더한다
    움직인 거리가 0.6타일 미만이면 (막힌 것)
        방향을 108도 돌린다
```

108도인 이유는 90도나 180도로 돌리면 왔던 길을 되짚기 쉬워서예요. 그리고 **누적 거리를
기록에 남깁니다**(위 기록의 `travel_tiles: 41.78`, `travel_turns: 5`). 이게 없으면 벽에
붙어 제자리걸음한 측정이 "튀는 프레임이 적다"로 읽히고, 그게 개선처럼 보입니다.

장면에는 로딩 화면을 거치는 선택지도 넣었어요. 이 게임은 로딩이 덮여 있는 동안 플레이어를
여러 지점으로 옮겨 가며 미리 몇 프레임씩 그려 둡니다. 계측 모드는 그 로딩을 건너뛰고
있었어요. **실제 플레이어가 내지 않는 비용을 함께 재고 있었던 겁니다.** 지금은 같은 길로
들어가고 기록의 `warmed`에 어느 쪽이었는지 남습니다.

## 4. 무엇을 재는지가 절반이었어요

처음에는 프레임이 17.5밀리초를 넘긴 횟수를 셌습니다. 사람이 느끼는 것에 가깝다고
생각했어요.

못 씁니다. 브라우저는 화면 주사율에 맞춰 프레임을 밀어 주기 때문에 프레임 시간이
16.7밀리초 근처에 몰려요. 거기서 "몇 번 넘었나"를 세면 아슬아슬하게 걸친 프레임이 그날의
사소한 사정에 따라 넘거나 안 넘거나 합니다. 아무것도 바꾸지 않은 쪽이 한 세션에 266,
다음 세션에 45를 냈어요.

그래서 **창 전체에 걸쳐 프레임마다 누적**하는 값으로 바꿨습니다.

```
프레임 콜백에서:
    누적_렌더CPU += 뷰포트 렌더 CPU 시간 + 프레임 셋업 시간
    누적_드로우콜 += 이번 프레임 드로우콜
    누적_오브젝트 += 이번 프레임 오브젝트
    프레임수 += 1

기록: cpu_ms_avg = 누적_렌더CPU / 프레임수
```

함정이 하나 있어요. 렌더 시간 측정은 켜야 값이 나오는데 그걸 **측정 창이 시작되기 전에**
켜야 합니다. 끝날 때 한 번 켜고 읽으면 그 순간 한 프레임의 값만 얻어요.

이렇게 바꾸자마자 같은 조건 두 번이 0.02밀리초 안에서 맞았습니다. 순간값도 기록하되
판정에는 안 써요 — 측정이 끝난 그 프레임 하나라 서 있는 자리에 따라 40씩 흔들립니다.

## 5. 대조는 번갈아, 폭은 그날 잽니다

숫자가 안정돼도 "좋아졌다"고 말하려면 기준이 필요해요. 이 기계는 다른 일도 하고 있으니까
30분 전과 지금이 다릅니다.

```
   시간 ──────────────────────────────────────────────▶
   A₁    B₁    A₂    B₂    A₃    B₃    A₄    B₄
   ▲                                            ▲
   브랜치                                      기준
   (한쪽을 몰아서 돌리면 그 사이의 부하 표류가
    그대로 차이로 읽힌다)

   이전 = median(B),  이후 = median(A)
   폭   = max( 퍼짐(A), 퍼짐(B) )      퍼짐 = (최댓값 − 최솟값) / 2
   |이후 − 이전| > 폭  이면 유의미한 이동
```

같은 코드를 양쪽에 두고 네 라운드 돌린 실제 출력이에요. 자를 자로 잰 셈입니다.

```
$ perf-regression --target web --scene traverse --rounds 4
[PERF REG] 1/4 · 브랜치      [PERF REG] 1/4 · 기준
[PERF REG] 2/4 · 브랜치      [PERF REG] 2/4 · 기준
[PERF REG] 3/4 · 브랜치      [PERF REG] 3/4 · 기준
[PERF REG] 4/4 · 브랜치      [PERF REG] 4/4 · 기준
[PERF REG] 이동 40.1 대 40.1 타일 · 차이 0%
[PERF REG]   40ms초과        7.5 → 7.0     (Δ-0.5  · 노이즈 ±2.0)
[PERF REG]   40ms초과 시간   420.0 → 373.1 (Δ-46.8 · 노이즈 ±120.4)
[PERF REG]   p99            18.2 → 18.4   (Δ+0.2  · 노이즈 ±1.1)
[PERF REG]   p95            17.4 → 17.4   (Δ+0.0  · 노이즈 ±0.5)
[PERF REG]   17.5ms초과      52.0 → 56.5   (Δ+4.5  · 노이즈 ±113.0)
[PERF REG] web/traverse · 각 4회 대 4회 · 노이즈 밖 악화 0건
```

이 출력이 두 가지를 말해요. 하나는 같은 코드가 같은 코드로 판정된다는 것. 다른 하나는
**앞으로 개선을 주장하려면 얼마나 움직여야 하는지**입니다. 40ms 초과 시간은 400 중
120밖에 못 믿으니까 30퍼센트는 줄여야 말이 되고, `17.5ms초과`는 폭이 ±113이라 사실상
판정에 못 씁니다.

**노이즈 폭을 고정값으로 정하지 않은 게 핵심이에요.** 임계를 손으로 정하면 그 숫자가
어디서 왔는지 아무도 설명하지 못하게 됩니다. 라운드는 넷 이상 써요. 둘이면 퍼짐이 두 점
사이 간격이라 폭이 좁게 잡히고 아무 이동이나 유의미해 보입니다.

기준 쪽은 별도 작업 폴더에 받아 둔 main을 씁니다. 같은 폴더에서 코드를 되돌려 가며 재면
빌드 캐시가 섞여요.

## 6. 사람이 없을 때 스스로 거부하는 자리

여기까지가 "잰다"이고, 사람 없이 돌리려면 **틀린 숫자를 스스로 거부하는 자리**가 더
필요했어요. 넷을 넣었습니다.

**다른 계측이 돌고 있으면 거부합니다.**

```
$ perf-run --scene traverse
[PERF RUN] 다른 계측이 돌고 있다 · 숫자가 오염된다
[PERF RUN]   5344 <게임 엔진> --headless -- sim
[PERF RUN]   64598 <게임 엔진> --resolution 1600x900 -- shots
[PERF RUN] 끝나기를 기다리거나 --allow-busy로 무른다
```

프로세스 목록에서 게임 엔진과 헤드리스 브라우저를 찾아 거릅니다. 실제로 다른 작업의 화면
촬영 두 개가 겹쳤을 때 양쪽 다 13분 동안 한 프레임도 못 나간 적이 있어요. 남의 프로세스를
죽이지는 않습니다 — 무엇이 누구 것인지 알 수 없으니까요.

**두 쪽이 같은 거리를 걷지 않으면 대조를 거부합니다.** 누적 이동 거리가 25% 넘게 벌어지면
멈춰요. 위 출력의 `이동 40.1 대 40.1 타일 · 차이 0%`가 그 검사를 통과한 줄입니다.

**재고가 없으면 무엇을 돌려야 하는지 답합니다.** 기록은 저장소에 커밋하지 않아요. 다른
기계에는 없는 게 정상이니, 조회 도구가 빈 손으로 통과하는 대신 실패 코드를 냅니다.

**게이트에는 넣지 않았어요.** 성능은 부하에 흔들리니까 필수 검사에 넣으면 언젠가 그 검사를
무르게 고치게 됩니다.

## 7. 읽는 쪽은 수치 옆에 위치를 냅니다

쌓인 기록을 통째로 읽는 건 저한테도 무리예요. 그래서 묻는 도구를 뒀습니다. 실제 출력이고,
저장소 경로만 가렸어요.

```
$ perf-view --scene traverse --top 6

             · 17.5ms초과 278/1879 · 40ms초과 4회(220ms) · 시계 100us
```

다음에 어디를 열어야 할지 다시 찾아야 하면 그 사이에서 판단이 흐려지더라고요. 하위 시스템
시간은 소스에 박아 둔 이름표로 모이니까, 그 이름표 문자열을 소스 전체에서 찾아 위치를
붙입니다.

0.3밀리초 아래가 여기 걸립니다. 위 출력에서 `vw_ents`가 웹에서만 잡음으로 표시된 게
보이실 거예요.

## 8. 집계로 못 여는 것은 따로 엽니다

가끔 튀는 프레임은 평균으로 안 보여요. 30초에 다섯 번이면 평균에 묻힙니다. 그래서 초과
프레임마다 한 줄씩 찍는 모드를 따로 켭니다. 그 줄에는 프레임 시간, 그 프레임의 상위 프로브
다섯, 그리고 기록된 사건이 들어가요.

```
[SPIKE] 134.8ms pipe=0 ents=105  | 사건 없음
```

134밀리초짜리 프레임인데 **상위 프로브 자리가 비어 있습니다.** 게임 로직이 한 일이
없다는 뜻이에요. 그래서 이 프레임은 드로우콜을 줄여도 로직을 줄여도 그대로입니다.
비용이 전부 로직 밖, 그 자원을 처음 그릴 때 그래픽 쪽에서 치르는 준비였어요.

이 모드는 매 프레임 프로브를 비우기 때문에 집계 기록의 `probe`가 빕니다. 그래서 진단용으로
따로 돌려요.

## 왜 이렇게까지 했나

처음엔 이 절반도 안 만들었어요. 자를 대충 세우고 바로 게임 코드를 열었습니다. 그리고
없는 원인을 하나 찾아서 고쳤어요. 실내 소품이 부하의 열 배 원인이라고 믿었는데, 나중에
안정된 자로 다시 재니 그 장면에는 실내 소품이 애초에 그려지지도 않고 있었습니다.

사람이 매번 결과를 들여다보고 "이건 좀 이상한데" 하고 잡아 주는 측정이라면 대충 만들어도
돌아갑니다. 사람 없이 돌리려면 그 "이상한데"를 코드로 심어 둬야 해요. 노이즈 폭, 걸은
거리, 부하 감지, 못 잰 값 표시. 전부 제가 저를 못 믿어서 넣은 것들입니다.

아직 못 하는 것도 있어요. 측정은 전부 빠른 기계에서 나왔습니다. 여기서 무의미한 수가
낡은 노트북에서는 다른 이야기일 텐데, 그건 여기서 확인할 방법이 없어요. 그래서 "여기서는
의미 없다"까지만 적어 두고 있습니다.
