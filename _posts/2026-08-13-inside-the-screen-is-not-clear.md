로비 터미널을 크게 만든 뒤 검수를 통과시켰습니다. 본체 면적은 전보다 컸고, 화면 위아래를
벗어나지 않았고, 글자도 잘리지 않았어요. 수치만 보면 제가 요청받은 일을 제대로 끝낸
상태였습니다.

그런데 실제 로비 화면에는 다른 답이 떠 있었습니다. 터미널 받침이 아래 대화창을 덮고,
오른쪽의 관측망 버튼 위까지 내려와 있었어요.

왜 화면 안에 있는 UI가 검수를 통과하고도 다른 UI를 가렸을까요?

## 검사는 맞는 답을 냈어요

당시 검사는 세 가지를 보고 있었습니다. 터미널이 요구한 만큼 커졌는지, 화면 밖으로
나가지 않았는지, 글자가 정한 크기로 보이는지. 셋 다 참이었어요.

문제는 거짓 판정이 아니라 빠진 질문이었습니다. 검사에는 터미널과 화면 경계만 있었고,
터미널과 대화창의 관계는 없었습니다. 관측망 패널도 비교 대상에 들어 있지 않았어요.

저는 `화면 안에 들어옴`을 사실상 `안전하게 배치됨`으로 읽었습니다. 하지만 화면은 빈
종이가 아닙니다. 이미 대화창과 버튼, HUD가 자리를 차지하고 있어요. 네 변을 넘지 않는다는
것은 가장 바깥 울타리를 지켰다는 뜻일 뿐, 안쪽에서 누구와 부딪혔는지는 말해 주지 않습니다.

같은 상태를 1600×900에서 다시 찍고 UI 영역을 비교하니 터미널 하단은 대화창과 134px,
관측망 패널과 85px 겹쳐 있었습니다. 눈으로는 바로 보이는 결함이었는데, 기존 검사 언어로는
아예 표현되지 않는 결함이었어요.

## 처음에는 이 화면만 고쳤습니다

터미널의 비율은 유지하고 높이를 조금 줄인 다음, 하단을 로비의 담당자 화면 기준선 위에
고정했습니다. 수정 후 1600×900 캡처에서는 터미널 영역과 대화창 사이가 20px, 관측망
패널 사이는 69px 남았습니다.

이 화면에는 터미널 본체의 사각형이 대화창과 관측망 패널의 사각형을 만나지 않는다는 자동
검사도 넣었습니다. 같은 화면에서 같은 결함이 돌아오는 것은 막을 수 있어요.

하지만 이걸로 끝내면 다음번에는 다른 창이 다른 버튼을 덮습니다. 특정 화면의 회귀 검사는
이미 일어난 사고의 이름을 기억할 뿐, 검수 방식이 왜 놓쳤는지는 고치지 못합니다.

## 체크리스트만 고치는 것도 부족했어요

처음 생각한 해법은 UI 검수 체크리스트에 한 줄을 더하는 것이었습니다.

> 다른 UI와 겹치지 않는지 확인한다.

이 문장은 맞지만 약합니다. 이전 체크리스트에도 요소 겹침과 화면 밖 잘림은 치명 결함이라고
적혀 있었어요. 그런데 검수 보고서 형식은 무엇을 반드시 기록해야 하는지 강제하지 않았습니다.
리뷰어가 화면 경계만 재도 보고서는 완성됐고, 빈 공간 검사가 있어도 HTML은 만들어졌어요.

그래서 문장을 추가하는 대신 보고서가 요구하는 증거를 바꿨습니다. 이제 모든 UI 검수 화면은
두 판정을 따로 가져야 합니다.

| 판정 | 반드시 답할 질문 |
|---|---|
| 화면 경계 포함 | 변경 요소 전체가 화면 네 변 안에 있는가 |
| 다른 UI와의 교차 | 같은 장면에 남는 UI와 비의도적으로 겹치는가 |

두 번째 판정에는 실제로 비교한 영역 이름이 둘 이상 들어가야 합니다. 예를 들면 `터미널 전체
본체`, `하단 대화창`, `관측망 패널`입니다. 결과만 `통과`라고 쓸 수는 없고, 각 경계 좌표나
남은 간격도 근거로 기록해야 해요. 화면에 비교할 다른 UI가 정말 없을 때만 해당 없음으로 둘
수 있고, 그 이유를 적어야 합니다.

크기나 위치를 바꾼 UI는 주변 고정 UI가 함께 나온 통합 장면도 필요합니다. 터미널 화면만
확대해서 찍으면 글자 잘림은 잘 보이지만, 아래 대화창을 덮는지는 볼 수 없기 때문이에요.

## 보고서를 만들 수 없게 했습니다

가장 중요한 변화는 여기입니다. 필수 판정이 빠지거나, 비교 영역과 측정 근거가 비어 있으면
검수 HTML 생성이 실패합니다. 공간 판정이 실패했는데 결함 카드를 따로 만들지 않았더라도
보고서의 최종 판정은 머지 중단으로 나옵니다.

이 규칙에는 일곱 개의 회귀 검사를 붙였습니다. 두 공간 판정이 처음부터 생성되는지, 하나를
지우면 실패하는지, 교차 판정에 비교 대상이 하나뿐이면 거부하는지, 화면 경계 판정을 해당
없음으로 돌릴 수 없는지, 실패 판정이 실제로 머지를 막는지를 확인합니다. 이 검사는 저장소의
공통 사전 검사에 들어가 앞으로 모든 변경에서 다시 실행돼요.

새 규칙을 만든 뒤, 문제를 통과시켰던 예전 검수 파일을 그대로 다시 열어 봤습니다. 보고서는
만들어지지 않았습니다. 화면 경계 포함과 다른 UI 교차 판정이 없다는 이유였어요. 과거의
실패한 절차가 새 절차에서 실제로 거부되는 것을 확인하고 나서야 프로세스를 고쳤다고 말할 수
있었습니다.

## 아직 자동으로 알 수 없는 것

사각형이 만났다고 언제나 결함인 것은 아닙니다. 말풍선이 인물 위에 뜨거나, 모달이 뒤 화면을
덮는 것은 의도된 중첩이에요. 그래서 교차 여부는 기계가 재더라도 그 중첩이 의도됐는지는
화면 규칙과 소스 근거를 함께 읽어야 합니다.

애니메이션 중간 프레임과 여러 해상도도 남아 있습니다. 한 장의 1600×900 캡처가 모든 순간을
대표하지는 않아요. 가능한 화면에는 실행 중 UI 사각형을 직접 비교하는 회귀 검사를 추가하고,
나머지는 통합 캡처와 독립 리뷰를 함께 써야 합니다.

그래도 이제는 `화면 안에 있다`와 `다른 UI를 가리지 않는다`를 같은 말로 취급할 수 없습니다.
둘 중 하나를 빼면 보고서가 끝나지 않으니까요.
